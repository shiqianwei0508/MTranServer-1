## 图片翻译 ENOENT 字体 bug 修复

- 现象：kylin 服务器部署的编译二进制（dist/main.js）做图片翻译时报 `ENOENT: ./noto-sans-sc-latin-400-normal-kf9x9bhb.woff2`。
- 根因：`src/services/image-translator.ts` 用 `readFile(asset.path)` 读字体，但 `asset.path` 来自 `type:'file'` 导入且**未用 `import.meta.url` 解析为绝对路径**；编译二进制下裸相对路径以 CWD 为基准找不到。engine.ts(bergamot.wasm)/detector.ts(cld2.wasm) 都用了 `path.resolve(currentDir, wasmPath)`，所以没报错。
- 修复：`src/assets/fonts.ts` 加 `path.resolve(currentDir, p)`（currentDir=path.dirname(fileURLToPath(import.meta.url))），导出路径全部绝对化；image-translator.ts 的 readFile 保持不变。
- 重要：必须重新 `bun run build`（编译）并替换二进制才生效，仅换字体文件无效。本机是 Windows，无法编译 linux 二进制。

## Docker 镜像优化 & 上游 build/Dockerfile 失配溯源

- `docker/Dockerfile` 多阶段构建：builder 用 `bun install --frozen-lockfile` → `bun run build:node` → `bun prune --production`（移除 dev 依赖，缩小镜像）；runtime 用 `node:22-slim` + 复制 `dist/` + `node_modules`（已 prune）。
- **关键坑**：`bun install --production` 不会删除已安装的 devDependencies（官方文档明确：dev 包仍留 node_modules，必须用 `bun prune --production` 才能真正移除）。第一次写成 `bun install --frozen-lockfile --production` 是无效的，已改为 `bun prune --production`。
- `prune --production` 只删 dev 部分，`dependencies` 与 `optionalDependencies`（如 `@img/sharp-linux-x64`）均保留，不影响运行时加载 sharp/onnxruntime 原生模块。
- **上游失配溯源**（用户指出 Dockerfile 原在根目录）：`1336ab64` 引入 OCR/sharp/onnxruntime 时，根 `Dockerfile` 只 `COPY dist`、不拷 node_modules、用 `node:22-alpine`，当时是自洽的——因为那时 `build:node` 没有 `--external`，依赖全打进 bundle。后来 `692630a`「fix: 改用 --node 构建模式以兼容原生模块」把 sharp/onnxruntime 改成 `--external`（bun 无法把 .node 二进制打进单文件 bundle），但 Dockerfile 没同步适配，导致"只拷 dist"缺 node_modules 跑不起来。fork 后重建 docker 目录才修好（拷 node_modules + slim + prune）。
- 结论：不是 1336ab64 本身的 Dockerfile 有问题，而是 692630a 改 build 方式后 Docker 构建没跟上。
